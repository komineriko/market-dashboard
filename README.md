## 日経225オプション SQ予測レポート

当限のオプション板から、SQに向けた需給構造を毎日組み直すレポート。

### 何を出しているか

| 区分 | 内容 |
| --- | --- |
| フォワード | プット・コール・パリティ（F = K + C − P）のATM近傍中央値 |
| IV | 清算値段から自前で逆算（データ提供元のIV列に依存しない） |
| スキュー | 固定モネネス（K/F）と固定デルタの2通りで正規化。RR25 / BF25 |
| GEX | ネットガンマのプロファイルとフリップ水準、ロング/ショートガンマの判定 |
| 壁 | ±375円で集計したOTMの厚み、Iron Condorの上下限、max_pain とその傾き |
| PUTブック | 実効デルタ・ベガ・理論プレミアム、および増減の**3分解** |
| SQ参考帯 | リスク中立分布から50%帯・80%帯。プレミアム法とIV法のクロスチェック付き |
| 前日比 | 捕捉窓の**積集合**だけで比較（窓の外に出た玉を増減と誤認しない） |
| 答え合わせ | 前日に立てた監視ポイントを、当日の値で自動評価 |

### 設計上こだわっている点

元レポートの読み方をそのまま実装している。

- **実効デルタの3分解** — 実効デルタが増えても、それが「新規に建てられた保険（ポジション要因）」なのか
  「現値が下がって既存玉のデルタが立ち上がっただけ（現値移動要因）」なのかを分ける。
  後者は相場が戻れば自動的に消えるので、防御力が増したとは読めない。
- **名目金額の前日比は使わない** — 現値が動くとOTMのプレミアムは機械的に動く。
  壁の増減は枚数と実効デルタで判定する。
- **共通窓での前日比** — 捕捉される行使価格の範囲は日々ずれる。積集合を取らないと窓の移動が増減に化ける。
- **固定行使価格のIV前日比は恐怖の指標に使わない** — 現値が動けば同じ行使価格でもモネネスが変わる。
  判定はモネネス正規化・デルタ正規化した量で行う。
- **取れなかったデータは黙って埋めない** — 未取得は「データ品質の開示」として明示する。

### 実行

```bash
python update_sq_report.py               # JPXから取得して更新
python update_sq_report.py --demo        # 合成データで動作確認（通信しない）
python update_sq_report.py --chain-file 225OP.xlsx   # 手元の板ファイルを使う
python update_sq_report.py --dry-run     # 書き込まずに結果だけ表示
python -m unittest discover -s tests     # テスト
```

### 環境変数

| 変数 | 用途 |
| --- | --- |
| `SQ_CHAIN_FILE` | 手元のオプション板ファイル（カンマ区切りで複数可）。長形式・横形式の両方に対応 |
| `SQ_JPX_DAILY_URL` | JPX日次相場情報ファイルのURLを直接指定 |
| `SQ_NIKKEI_VI` | 日経VI。自動取得できない場合の手入力 |
| `SQ_EVENTS_FILE` | イベント一覧のJSON（既定 `sq_events.json`） |

### 生成物

| ファイル | 内容 |
| --- | --- |
| `sq_report.html` | レポート本体。`AUTO_UPDATE_DATA` ブロックだけが書き換わる |
| `sq_snapshots/chain_YYYYMMDD.json` | 板の全量。前日比と3分解に使う。直近15営業日ぶんだけ保持 |
| `sq_history.json` | 主要指標の軽量な履歴 |
| `sq_events.json` | SQまでの日程（手で編集する。空でも動く） |

2026-08-18 を基準日として、同日を扱った既存レポートと突き合わせた結果:

| GEXフリップ | 67,327 | 67,353 |
| 中期レンジ 天井 | 75,000（net +5,453） | 75,000（net +5,450） |
| 中期レンジ 床 | 60,000（net −10,914） | 60,000（net −10,895） |
| 26-11 建玉 CALL/PUT | 6,742 / 13,618 | 6,679 / 13,129 |

建玉と価格が独立に正しくないとネット建玉はここまで一致しない。
残る差は捕捉窓の広さと、突き合わせ先がナイトセッションのスナップショットを
使っていることによる（本実装は清算値段ベース）。

### データの所在（実地調査の結果）

JPXの公表データは置き場所が分かりにくいので、調べた結果を残しておく。

| 必要なもの | 取得先 | 形式 |
| --- | --- | --- |
| 行使価格別の**建玉**・清算価格 | 大阪取引所日報 `Daily_Report_OSE_YYYYMMDD.zip` 内の `siop_dyr_*.pdf` | **PDF** |
| 清算値段・IV・原資産価格・金利・残日数 | 清算値段ページの `rbYYYYMMDD.csv` | CSV (cp932) |
| 日経平均の四本値 | yfinance `^N225`（Stooqにフォールバック） | — |
| 取引参加者別ネット建玉 | `{日付}_indexfut_oi_by_tp.xlsx`（**週次**・金曜ベース） | xlsx |

- 行使価格別の建玉は、日次ではPDFにしか無い。建玉残高のExcelは日次公開ではなく、
  「日次相場情報」のページにはデータファイルが置かれていない。
- 日報PDFには**競争売買市場**と**J-NET市場**の2つの表が入っている。J-NET市場の表は
  始値・高値・安値・終値・取引高・取引金額しか持たず、清算価格も建玉も列が無い。
  区別せずに読むと取引金額（円）を建玉として拾う。しかもこの並びは
  「清算価格は小数点あり／建玉は整数」という形の検証を満たしてしまうため、
  市場の見出しでページを切り分けている。
- 日報の1行は前日比の符号でトークン数が変わる。中間列は解釈せず、
  左から4つ（限月・最終日・行使価格・コード）と右から3つ
  （清算価格・権利行使数量・建玉残高）だけを読む。
- JPXはこれらのページをJSONインデックス経由で描画しており、URLは決め打ちできない。
  索引を辿って最新のファイルを探す実装にしてある。
- 取得が壊れたときは `tools/probe_jpx.py` で所在を調べ直せる。

### 制約

- **日報は当日中に公開されず、実測では翌営業日に出る。** そのためレポートは常に
  1営業日遅れになる。板・現物・前日比はすべてその日付で揃えている。
  金曜分を土曜に取り込むため、定期実行は月〜土に回している。
- **取引参加者別ネット建玉**は週次公表で、証券会社単位・売超買超それぞれ上位15社のみ。
  市場全体の集計ではなく、自己玉と顧客玉も区別できない。個別ファンドの建玉は
  日本のデリバティブでは公開されていない。ミニは1/10、マイクロは1/100でラージ換算している。
- **日経VI**は自動取得が不安定なため、既定では未取得として開示する。
  引け直前の水準を `SQ_NIKKEI_VI` で渡すと反映される（終値は引けの歪みを含むので推奨しない）。
- **参加者別手口・先物ネット建玉**は自動取得の対象外。誰が動いたかの検証は行っていない。
- 壁スコアは建玉・名目金額・現値からの近さを合成した独自の相対指標で、同じ日の中の序列としてのみ意味を持つ。
- Net GEX は「ディーラー = +CALL建玉 − PUT建玉」の慣例仮定に依存する。

本レポートは建玉スナップショットに基づく構造分析であり、投資勧誘・売買推奨ではありません。
